# 团队开发约定

## 分支与合并

- `main` 始终保持可编译、可启动。
- 功能分支使用 `feature/<module>-<topic>`，修复分支使用 `fix/<module>-<topic>`。
- 一个分支只处理一个清晰任务，通过 Pull Request 合并。
- 合并前至少执行后端测试、前端类型检查和构建。

## 分阶段并行

### 第一阶段：各自建立可用主流程

- 方向一实现挂号、患者队列、接诊、病历和诊断；基础数据暂时使用种子数据或测试夹具，不等待方向二完成全部维护页面。
- 方向二优先实现科室、员工、疾病、药品和医技项目查询，再补维护功能、用户角色和操作日志。
- 方向三优先实现医技队列和库存持久层，再实现接收、执行、结果、发药和退药。

### 第二阶段：按状态机对接

- 方向一负责创建医技申请、处方和收费项目。
- 方向一负责支付、退费以及缴费状态向医技和处方业务的协调。
- 方向三只负责医技申请和处方缴费后的执行状态，不处理收费逻辑。
- 方向二提供稳定的基础数据读取能力，不直接参与门诊业务状态更新。

### 第三阶段：集成与验收

- 仓库持有者负责端到端联调、契约一致性检查和核心流程验收测试。
- 各方向负责人修复本模块缺陷，并为关键状态流转补充回归测试。
- 合并到 `main` 前必须完成挂号到就诊、收费到执行、发药到库存流水的主路径验证。

## 功能板块验收

- 每完成一个功能板块，先补齐或更新本模块自动化测试，再进入下一板块开发。
- 后端板块至少覆盖应用服务、状态流转、Mapper 条件更新和异常分支；库存、收费等高并发或资金相关逻辑必须覆盖失败场景。
- 前端板块至少完成类型检查和构建验证；涉及关键交互、表单提交或状态按钮时，应补充对应组件或页面测试。
- 自动化测试未通过时，不提交功能 PR，不进入下一板块；确因本地环境缺失无法执行时，必须在 PR 中说明未验证项和原因。

### 方向三基础验收清单

方向三优先保证医技执行、药房发退药和库存基础管理三条最小闭环可用；统计看板、报表分析等属于后续增强，不作为基础功能必做项。

- 医技：可按类型、状态、申请号或挂号 ID 查询申请；支持已缴费申请接收、已接收申请执行、已执行申请录入结果；非法状态流转返回稳定业务错误。

- `docs/api/openapi.yaml` 是接口源契约。需要改字段或状态时先提交契约 PR，再写实现。
- 方向一在门诊模块创建 `check_request`、`inspection_request`、`disposal_request` 和 `prescription`。
- 方向三在医技或药房模块更新上述记录的执行字段和后续状态。
- 双方可各自维护本模块所需 Mapper，但不得调用或注入对方 Mapper；跨模块动作通过应用服务完成。
- 每张表的其他写操作遵守 `docs/architecture.md` 的所有权定义。
- 新迁移只新增 Flyway 文件，不修改已推送的基线迁移；文件名使用各自时间戳。
- 每个成员使用独立数据库或独立 schema，避免本地测试数据互相覆盖。

## 接口约定

- API 前缀统一为 `/api`。
- 返回体使用 `ApiResponse<T>`。
- 列表分页参数统一使用 `page`、`size`。
- HTTP 状态码表达请求结果，业务错误同时返回稳定的 `code`。
- 日期时间使用 ISO 8601 字符串，数据库统一按 `Asia/Shanghai` 解释。
- 状态流转在后端校验，前端隐藏按钮不能代替权限或状态检查。

## 持久层约定

每个业务模块使用相同目录结构：

```text
src/main/java/com/hospital/his/<module>/persistence/
├── mapper/                    # MyBatis Mapper 接口，只在所属模块内使用
└── model/                     # 数据库行映射和写入参数，不作为 API DTO
src/main/resources/mapper/<module>/
└── *Mapper.xml                # 查询、写入及状态条件 SQL
```

- 查询结果命名为 `*Row`，写入参数命名为 `*Draft`；API 请求和领域对象不得直接复用持久化模型。
- Mapper 接口使用 `Optional<T>` 表示单条可空结果，写操作返回受影响行数。
- 分页统一使用 `PageQuery` 和 `PageResult`，SQL 使用 `LIMIT`、`OFFSET`，列表查询必须有稳定排序。
- 新增记录需要回传主键时，`*Draft` 使用可写的 `id` 并配置 `useGeneratedKeys`。
- 状态流转 SQL 必须在 `WHERE` 中带当前状态，影响行数为 `0` 时由应用服务返回 `INVALID_STATE_TRANSITION`。
- 库存等高并发数据必须带版本条件，并在同一事务中写业务数据和流水。
- XML 中不得使用 `${}` 拼接用户输入。动态排序、表名等只能从后端固定白名单选择。
- 应用服务负责 `@Transactional` 边界，Controller 不直接注入 Mapper。

当前可复制的参考实现：

- `DepartmentMapper`：CRUD、动态筛选、分页和生成主键。
- `RegistrationMapper`：按旧状态更新挂号状态。
- `MedicalRecordMapper`：按一次就诊保存和更新病历。
- `CheckRequestMapper`：医技队列和条件状态流转。
- `DrugStockMapper`：库存非负校验与乐观锁。
